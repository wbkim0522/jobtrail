# ADR 001: AI Agent 기반 개발 방식 도입

- **Title:** AI Agent 기반 개발 방식 도입
- **Status:** Accepted — Human 승인
- **Date:** 2026-11-24
- **Accepted Date:** 2026-11-25 (Asia/Seoul)

## Context

Jobtrail은 기존에 개발된 개인 프로젝트이며 앞으로 기능을 지속적으로 개선·확장한다. 개발자가 모든 코드를 직접 작성하는 방식에서 Agent가 분석부터 구현·검증·문서화까지 주도하는 방식으로 전환하려 한다. 이는 이번에 정한 전환 방향이며, 과거 작업별 AI 사용 여부나 개발 시간을 조사했다는 의미는 아니다.

[현재 상태 분석](../architecture/current-state.md)과 저장소 확인상 자동 테스트 및 CI는 아직 없다. 기존 build/lint는 실행할 수 있지만 기능의 정확성을 충분히 보증하지 않는다. 개발 위임 범위를 넓히면서도 요구사항, 변경 이유, 검증 근거를 남길 수 있는 절차가 필요하다.

목표는 AI 사용량 확대가 아니라 생산성, 품질, 유지보수성, 재현성과 추적 가능성 개선이다. 이 프로젝트는 AI 개발 프로세스의 설계·운영 경험을 보여주는 포트폴리오로도 활용한다. 실제 측정 전에는 개선 효과를 성과로 주장하지 않는다.

## Decision Drivers

- Human이 제품 요구·우선순위·주요 기술 결정에 집중할 수 있는가.
- Agent의 일반 구현 판단을 충분히 위임하면서 데이터·운영 위험을 통제할 수 있는가.
- 수용 조건과 객관적인 검증으로 결과를 평가할 수 있는가.
- 작은 프로젝트에서 도구·조정·문서 관리 비용이 과도하지 않은가.
- 작업과 결정의 근거를 저장소에서 추적하고 다음 세션에서 이어갈 수 있는가.
- AI 비용과 Human 검토·수정 비용을 포함해 지속 가능한가.

## Considered Options

아래는 방식에 대한 비교이며 이 프로젝트에서 실시한 비교 실험 결과가 아니다.

| 선택지 | 작업 주도권 | 기대 이점 | 제약·위험 |
| --- | --- | --- | --- |
| 직접 개발 | Human이 분석·설계·코딩·검증 주도 | 세부 판단을 직접 통제 | 개발 전 과정에 Human 시간을 투입해야 함 |
| AI 보조 개발 | Human이 작업을 세분화하고 AI에 일부 생성·질의 위임 | 제한된 범위에서 점진적으로 AI 활용 | 단계 연결·컨텍스트 전달·검증 조정 부담이 Human에게 남음 |
| AI Agent 기반 개발 | Human이 목표와 경계를 정하고 Agent가 개발 과정 주도 | 일관된 흐름으로 분석·구현·검증을 위임할 가능성 | 잘못된 가정의 전파, 자체 리뷰 편향, 검증 누락과 비용 증가 가능성 |

## Decision

다음은 Human이 제시한 도입 방향을 기록한 것이다. Human은 2026-11-25에 이 결정을 승인했으며, 이 ADR의 공식 수용 상태는 **Accepted**다.

1. AI Agent 기반 개발을 선택한다. Human은 Product Owner로서 요구사항·우선순위·주요 기술적 의사결정·최종 승인을 담당한다. Agent는 분석·설계·구현·테스트·자체 리뷰·문서화를 주도한다.
2. 초기 개발 도구는 **Codex CLI**, 운영 단위는 **단일 Agent**로 한다. 일반 구현 판단은 [AGENTS.md](../../AGENTS.md)의 승인 경계 안에서 Agent에게 위임한다.
3. 신규 기능 확장에 앞서 자동 테스트와 CI 등 객관적인 품질 검증 환경을 구축한다. 구체적인 도구·범위·설정은 후속 작업에서 결정한다.
4. [단일 Agent 작업 절차](../ai-workflow/development-workflow.md)로 작업과 증거를 기록해 먼저 운영 방식을 검증한다.
5. 멀티 에이전트, 독립 리뷰, 작업 환경 격리, 오케스트레이션은 측정된 필요에 따라 검토한다. 현재 운영에 포함하지 않는다.

현재 저장소에는 개발 지침과 상태 분석, build/lint가 있다. Codex CLI 선택은 이후 개발 도구에 대한 결정이며, 설치·설정 검증이나 도입 효과 측정이 끝났다는 뜻은 아니다. Vitest, GitHub Actions, Git Worktree, Herdr, Multi-Agent Orchestration의 적용을 이 ADR로 확정하거나 구현하지 않는다.

## Consequences

**기대 효과:** 일반 개발 작업의 위임, 반복 가능한 검증 절차, 결정·변경·결과의 연결, Human 개입이 필요한 지점의 명확화. 이는 아직 검증되지 않은 기대다.

**단점과 위험:** 컨텍스트 정리·검토에 시간이 들고 AI 사용 비용이 발생한다. Agent가 잘못된 요구 해석을 구현과 테스트에 동시에 반영할 수 있다. 같은 Agent의 자체 리뷰는 독립 검토가 아니며 빌드 성공만으로 결함을 놓칠 수 있다. 과도한 문서화나 도구 도입이 오히려 작은 작업을 지연시킬 수 있다.

## Mitigation

- 작업별 수용 조건과 범위 제외 항목을 먼저 정하고 코드·검증 근거와 연결한다.
- [컨텍스트 표준화 ADR](002-standardize-agent-context.md)에 따라 지침·현황·결정·요구사항의 역할을 나눈다.
- 기존 승인 경계를 유지하고 운영 데이터 대신 분리된 테스트 환경과 합성 데이터를 사용한다.
- 품질 환경 구축 시 정상·경계·실패 조건의 회귀 테스트와 CI 검증을 마련한다. 구현 내용만 반복 확인하는 테스트로 충분하다고 간주하지 않는다.
- 초기에는 Human 최종 검수로 자체 리뷰의 한계를 보완하고, 검토에서 놓친 결함이 반복되면 독립 리뷰를 검토한다.
- 작은 작업 단위로 진행하며 비용·검토 부담을 기록한다. 공개 포트폴리오에는 검증 가능한 결과만 남기고 인증 정보·개인정보는 제외한다.

## Evaluation

아직 비교 기준선, 목표치, 성과 측정값은 없다. 아래는 평가 후보이며 기록 정의는 [작업 기록 방법](../ai-workflow/development-workflow.md#작업-기록과-측정)에 따른다.

| 평가 후보 | 관찰할 내용 |
| --- | --- |
| 생산성 | 유사한 범위·난이도 작업의 개발 경과 시간, 최종 승인까지의 시간, 완료 작업 수 |
| 직접 개입 시간 | Human의 요구 정리·추가 설명·기술 결정·리뷰·직접 수정에 쓴 시간 |
| 요구사항 누락 | 합의된 수용 조건 중 검토에서 누락이 확인된 항목 수; 사후 요구 변경과 구분 |
| 검토 중 발견 결함 | Agent 자체 리뷰와 Human 리뷰에서 발견한 고유 결함 수, 심각도, 발견 단계 |
| 수정 반복 횟수 | 검증·리뷰 피드백 후 수정하고 다시 검증한 회차와 원인 |
| 검증 결과 | 명령별 통과·실패·미실행, 첫 검증과 최종 검증 결과, 승인 후 발견된 회귀 |
| AI 사용 비용 | 작업별 확인 가능한 사용량·금액·산정 근거, 측정 불가 항목 |
| 유지보수·추적 가능성 | 요구사항→diff→검증→승인 연결 여부, 문서 오류와 재설명 필요 여부 |

초기 작업 기록을 기준선으로 삼고 이후 유사 작업끼리 비교한다. 직접 개발 방식과 실제 비교하지 않았다면 절감률을 추정해 발표하지 않는다. 결함 발견 수가 증가한 것은 검토 강화의 결과일 수도 있으므로 단독으로 품질 악화로 해석하지 않는다. 평가 주기, 허용 비용, 도입 확대 기준은 Human이 기록을 검토하며 정한다.
