# ADR 002: AI Agent 개발 컨텍스트 표준화

- **Title:** 저장소 기반 Agent 개발 컨텍스트 표준화
- **Status:** Accepted — Human 승인
- **Date:** 2026-11-24
- **Accepted Date:** 2026-11-25 (Asia/Seoul)

## Context

[Agent 기반 개발 도입](001-adopt-ai-agent-development.md)에 따라 작업을 세션 간 이어가고 결정 근거를 검토할 수 있어야 한다. 개별 프롬프트와 대화에만 지식이 있으면 다음 작업에서 규칙을 재전달해야 하고, 어떤 판단이 유효한지 확인하기 어렵다. 이는 해당 방식의 구조적 위험이며 Jobtrail에서 실제 누락 사고를 측정했다는 주장은 아니다.

현재 저장소에는 [AGENTS.md](../../AGENTS.md)와 [current-state.md](../architecture/current-state.md)가 있다. 전자는 개발 지침이고 후자는 특정 시점의 소스 분석이다. 두 문서를 모두 영구적인 구현 사실이나 승인된 기능 요구로 해석하지 않도록 역할을 구분해야 한다.

## Decision Drivers

- 세션이 달라져도 필요한 규칙과 근거를 찾을 수 있을 것.
- 실제 구현, 규범, 결정 상태, 작업 요구를 구분할 것.
- 코드 변경과 문서 변경을 함께 리뷰할 수 있을 것.
- 전체 문서를 매번 읽지 않아도 작업에 필요한 맥락을 선택할 수 있을 것.
- 소규모 프로젝트에 맞는 작성·갱신 비용을 유지할 것.

## Considered Options

| 방식 | 이점 | 한계 |
| --- | --- | --- |
| 프롬프트·대화 중심 | 시작이 간단함 | 지속되는 규칙과 일회성 지시를 재사용·추적하기 어려움 |
| 단일 대형 컨텍스트 문서 | 한 위치에서 조회 가능 | 현황·규칙·이력이 섞이고 중복·노후화·읽기 비용이 커질 수 있음 |
| 역할별 저장소 문서 + 작업별 요구 | 변경 이력과 책임을 나누고 필요한 부분만 참조 가능 | 참조 연결과 정합성 관리가 필요함 |

## Decision

역할별 저장소 문서를 공통 컨텍스트로 삼고 작업별 요구사항을 연결한다. 이는 Human이 제시한 표준화 방향을 구체화한 결정이며, 2026-11-25 Human 승인에 따라 ADR 상태는 **Accepted**다.

| 자료 | 담당하는 질문 | 관리 방식 |
| --- | --- | --- |
| `AGENTS.md` | 어떤 규칙과 승인 경계로 개발하는가? | 지속적인 규칙. 세부 버그·작업 이력을 쌓지 않음 |
| `docs/architecture/current-state.md` | 분석 시점의 구현과 검증 상태는 무엇인가? | 날짜·기준 커밋·사실/추정/미검증을 명시한 스냅샷 |
| `docs/adr/` | 왜 이 방향을 선택했으며 승인 상태는 무엇인가? | 대안·근거·결과·상태 기록. 제안을 확정 결정처럼 인용하지 않음 |
| `docs/ai-workflow/` | 작업을 어떤 순서로 수행·검증·보고하는가? | 단계별 입력·산출물·진입 조건. 개발 규칙은 복제하지 않고 참조 |
| GitHub Issue 또는 요구사항 문서 | 이번 작업에서 무엇을 완료해야 하는가? | 목표, 우선순위, 범위, 수용 조건, 변경된 요구와 결과 연결 |
| 실제 소스·설정·검증 로그 | 현재 무엇이 구현되어 있고 무엇을 확인했는가? | 구현 사실의 확인 근거. 기존 구현을 곧바로 바람직한 규칙으로 보지는 않음 |

작업 시작 시 `AGENTS.md`와 관련 요구사항을 읽고, 영향받는 소스와 필요한 현황·ADR만 확인한다. 대화에서 나온 지속적인 결정은 승인 상태와 근거를 적절한 문서에 남긴다. 대화 전체를 저장소에 복사하지 않는다.

## Consequences

**기대 효과:** 반복 설명 감소, 세션 간 작업 연속성, 판단 근거 추적, 코드와 문서의 함께 검토, 포트폴리오에서 과정과 결과를 구분한 설명이 가능해진다. 실제 감소량이나 품질 개선은 아직 측정하지 않았다.

**위험:** 문서가 코드보다 오래될 수 있고, 지침을 복사하면 서로 충돌할 수 있다. 과도한 컨텍스트는 읽기 비용을 높이고 중요한 요구를 가릴 수 있다. Proposed ADR을 확정 정책으로 오해하거나 현황 분석의 추정을 구현 사실로 받아들일 위험도 있다.

## Mitigation: 정합성 유지

1. 작업 계획에서 영향받는 문서를 확인한다. 규칙은 `AGENTS.md`, 주요 판단은 ADR, 절차는 workflow, 기능 요구는 해당 Issue/문서에서 관리한다.
2. 같은 규칙을 여러 곳에 복제하지 않고 상대 경로로 참조한다. 버전·명령은 현재 설정과 대조한다.
3. 작업 종료 리뷰에서 링크, 명령, 구현 상태, 승인 상태를 확인한다. 실제 소스와 문서가 다르면 차이를 기록하고 원인을 확인한다. 문서의 과거 상태를 현재 사실로 주장하지 않는다.
4. 현황 분석을 갱신할 때는 기준 날짜·커밋·검증 범위도 함께 갱신한다. 과거 빌드·테스트 결과를 새 변경의 검증으로 사용하지 않는다.
5. 승인된 ADR의 핵심 결정을 바꿀 때는 후속 ADR과 상호 참조로 변경 이유를 남긴다. 기존 결정의 이력을 조용히 덮어쓰지 않는다.
6. 요청이 문서 변경 범위를 제한하면 관련 문서를 임의로 수정하지 않고 후속 갱신 필요를 보고한다. 승인 여부가 불명확한 주요 결정은 Human에게 확인하며, 영향을 받지 않는 작업은 계속한다.

문서의 자동 수집·요약 도구나 별도 컨텍스트 관리 서비스를 도입한 상태는 아니다. 초기에는 Git diff와 Agent 자체 리뷰, Human 검토로 관리한다.

## Evaluation

작업 기록에서 문서의 잘못된 설명으로 인한 재작업, 동일 규칙의 중복·충돌, 반복 설명이 필요했던 항목, 요구사항·diff·검증·승인 참조의 누락을 관찰한다. 문서량 자체를 성과 지표로 삼지 않는다. 실제 기록을 근거로 문서 분할·통합 또는 자동 링크 검사 필요성을 검토한다.
