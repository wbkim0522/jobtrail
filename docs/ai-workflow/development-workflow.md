# 단일 AI Agent 개발 절차

작성일: 2026-11-24  
승인일: 2026-11-25 (Asia/Seoul)  
상태: 초기 운영 절차 — Human 승인. 운영 성과를 검증한 문서는 아니다.

## 적용 범위와 현재 상태

이 문서는 [AGENTS.md](../../AGENTS.md)를 실제 작업 순서로 연결한다. 아키텍처·보안·코딩·승인 규칙은 해당 문서를 참조하며 새로운 승인 경계를 만들지 않는다. 도입 배경은 [ADR 001](../adr/001-adopt-ai-agent-development.md), 컨텍스트 역할은 [ADR 002](../adr/002-standardize-agent-context.md)에 기록한다. 두 ADR은 Accepted 상태다.

| 구분 | 내용 |
| --- | --- |
| 정해진 방향 | Codex CLI를 초기 도구로 선택하고 단일 Agent가 분석·설계·구현·검증·자체 리뷰·문서화를 주도 |
| 현재 확인된 기반 | 기존 앱, 개발 지침·현황 분석, `npm run lint`, 타입 검사를 포함하는 `npm run build`, Vitest 단위 테스트 `npm test` (JT-001) |
| 먼저 구축할 항목 | CI 및 실패 차단 품질 관문. GitHub Actions는 JT-001 범위 밖이며 후속 작업 |
| 향후 검토 | 멀티 에이전트, 독립 리뷰, 환경 격리, 오케스트레이션, 자동화된 병합 품질 관문 |

초기 절차 문서 작성에서는 도구를 구성하지 않았으며, 이후 JT-001에서 테스트 환경을 구현했다. 결정과 검증 상태는 [ADR 003](../adr/003-adopt-vitest.md) 및 [작업 기록](../tasks/JT-001.md)을 참조한다. 한 Agent의 자체 리뷰를 독립 리뷰로 표기하지 않는다.

## 역할

- **Human:** 제품 목표·우선순위·수용 조건을 정하고 중요한 모호성을 해소한다. 주요 기술 결정, 승인 대상 작업, 최종 결과 수용을 판단하고 직접 개입 시간을 기록한다.
- **Agent:** 요구를 실행 가능한 작업으로 정리하고 분석부터 결과 보고까지 주도한다. 일반 구현 선택은 자율적으로 수행하며 관찰한 사실·가정·미검증을 구분한다. 검증 자료와 작업 기록 초안을 남긴다.

## 작업 순서와 단계별 산출물

| 단계 | 입력 | 수행 및 산출물 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 1. 요구 정리 | Human 요청, Issue/요구사항 문서 | 첫 실행 명령으로 시작 시각·시간대 확인 및 작업 기록. 목표·범위·제외 범위, 수용 조건 ID, 검증 방법, 미결정 사항 정리 | 제품 의미와 범위가 명확함. 중요한 모호성은 확인하고 나머지 구현 가정은 기록 |
| 2. 시작 상태 확인 | 요구와 저장소 | `git status --short`, 현재 브랜치·HEAD·관련 diff, `AGENTS.md`, 관련 문서·소스·scripts 확인. 기존 변경과 작업 대상 구분 | 선행 변경을 보존하며 작업 가능. 충돌하면 영향을 받는 수정 전에 해결 |
| 3. 분석·계획 | 소스 근거, 수용 조건 | 변경 위치·데이터 흐름·예외 처리·검증 계획·문서 영향·승인 필요 항목 | 일반 작업은 Agent 판단으로 진행. 승인 대상 작업은 검토안을 준비하고 해당 변경 전에 승인 |
| 4. 구현 | 계획과 필요한 승인 | 최소 범위 diff, 필요한 테스트·문서 변경, 가정·범위 변경 기록 | 수용 조건을 검증할 수 있는 구현 준비. 환경 구축 작업은 구성 자체의 수용 조건 적용 |
| 5. 검증 | 변경 코드와 검증 계획 | 적용 가능한 build/lint 및 도입된 관련 테스트 실행. 수용 조건별 결과·명령·실패·경고 기록 | 필수 검증 통과. 실패는 아래 수정 절차로, 환경 부족은 검증 대기로 처리 |
| 6. 자체 리뷰 | 전체 diff, 수용 조건, 검증 결과 | 요구 누락·보안·데이터 경계·오류 처리·회귀·문서·무관한 변경 점검. 발견 사항과 수정 기록 | 관련 중대 결함 없음. 수정했다면 영향받는 검증 재실행 후 결과 최신화 |
| 7. 결과 보고 | 리뷰된 diff와 증거 | 검증·리뷰 종료 시각 및 경과 시간 기록. 상세 근거는 작업 기록·ADR에 유지하고 아래 최종 보고 기준에 따라 요약 | Human이 결과와 한계를 검토할 수 있음. 검증 불가를 완료로 포장하지 않음 |
| 8. Human 검수·Git 반영 | 결과 보고와 변경사항 | 수용/수정 요청/보류 기록. 승인 범위에 맞는 commit·병합·배포 관리 | 최종 수용을 기록. 병합·배포는 별도 승인 경계 확인 후에만 실행 |

작업별 계획에 대한 일괄 사전 승인을 요구하지 않는다. 승인 대상 변경만 분리하고 안전하게 진행 가능한 분석·구현은 계속한다.

### 요구사항 및 수용 조건

Issue 또는 요구사항 문서에 다음을 간단히 적는다. 채팅 요청으로 시작했다면 Agent가 먼저 정리하고, 지속적인 기록이 필요한 내용은 허용된 작업 범위 안에서 연결한다.

```text
작업 ID / 제목:
목표 및 사용자 가치:
우선순위:
포함 범위 / 제외 범위:
수용 조건:
- AC-1: [전제]에서 [행동]하면 [관찰 가능한 결과]
- AC-2: [경계·실패 상황]에서 [기대 결과]
조건별 검증 방법:
미결정 사항 / 가정:
승인 필요 항목 및 승인 근거:
```

“잘 동작한다” 대신 화면 결과·데이터 변화·실패 처리처럼 확인 가능한 조건을 사용한다. 기존 요구의 누락과 작업 중 새로 추가된 요구를 구분한다. README의 향후 계획만으로 구현 범위를 늘리지 않는다.

### 현재 검증과 실패 처리

현재 실행 코드·테스트·의존성·관련 설정 변경에는 `npm run lint`, `npm run build`, `npm test`를 실행한다. build에는 테스트 파일·설정의 `tsc -b` 타입 검사도 포함된다. `npm test`는 사용자 입력 없이 한 번 실행 후 종료하며, 개발 중 감시 모드는 `npm run test:watch`로 실행한다. 문서만 변경할 때는 지침에 따라 내용·링크·명령·변경 범위를 검토하고 자동 검증 생략 사유를 기록한다.

실패하면 다음 순서로 처리한다.

1. 실패 명령·증상·재현 조건을 기록하고 이번 변경, 기존 결함, 환경 문제, 요구 해석 문제 중 근거가 있는 원인을 좁힌다.
2. 원인에 맞는 최소 수정을 수행한다. 검사 비활성화나 오류 은폐로 통과시키지 않는다.
3. 관련 검증을 재실행하고 수정 회차·결과를 기록한다. 실패가 반복되면 새 근거 없이 같은 수정을 반복하지 말고 가설을 재검토한다.
4. 권한·제품 결정·승인 부족으로 진행할 수 없으면 필요한 입력과 영향을 명시한다. 필수 검증이 끝나지 않은 작업은 검증 대기로 보고한다.

품질 환경 구축 작업은 별도로 정의한다. 테스트 도구·대상·CI 실행 조건·안전한 테스트 데이터를 정한 뒤 구현하며, 통과뿐 아니라 실패가 검출되는지도 확인한다. 의도적 실패 검증은 임시 파일로 수행하고 결과를 기록한 뒤 제거하여 최종 테스트를 다시 실행한다. 범위 밖의 기존 결함은 재현 증거와 후속 회귀 테스트 계획으로 남긴다. 현재 단위 테스트는 집계·날짜 함수 대상이며 운영 DB나 외부 서비스에 의존하지 않는다.

### Human에게 전달하는 최종 보고

최종 보고는 다음 다섯 항목을 중심으로 간결하게 작성한다.

1. 구현 완료 내용
2. 주요 변경 파일 (검토할 파일 링크)
3. 검증 결과 (실제 통과·실패·미실행 및 생략 이유)
4. 발견된 문제 및 미해결 사항
5. Human이 판단하거나 확인해야 할 사항 (없으면 없음을 명시)

상세 명령·실행 이력·수용 조건별 증거·측정값은 작업 기록에, 기술 도입의 배경·대안·선택 근거·제약은 ADR에 유지한다. 최종 보고에는 판단에 필요한 핵심과 상세 문서 링크를 남기고 같은 내용을 반복하지 않는다. 간결함을 이유로 실패·미검증·잔여 위험을 생략하지 않는다. 이미 승인된 결과를 재승인 요청으로 되돌리지 않는다.

### Human 승인과 Git 변경사항 관리

- 시작과 종료 시 기존 변경과 Agent 변경을 구분한다. 작업에 무관한 변경을 정리하거나 되돌리지 않는다.
- commit을 수행하는 작업에서는 대상 diff를 먼저 검토하고 관련 파일만 stage한다. 커밋 메시지와 작업 기록을 연결하며, commit하지 않았다면 그 상태를 보고한다. 단순 파일 작성 요청을 병합·배포 허가로 해석하지 않는다.
- 기본 브랜치 병합·실제 배포와 자동 배포를 유발하는 작업은 [승인 규칙](../../AGENTS.md#8-human-approval-required)을 따른다. 기존 문서의 자동 배포 설명이 있다면 원격 동작을 확인하기 전에 안전하다고 추정하지 않는다.
- Human이 수정 요청하면 해당 수용 조건과 이유를 기록하고 구현·검증·리뷰 단계로 돌아간다. 승인된 결과 이후 코드를 다시 바꾸면 추가 변경과 검증 상태를 드러낸다.
- 작업 브랜치 이름, commit 형식, PR 자동 생성, Git Worktree 사용을 이미 정해진 정책으로 가정하지 않는다. 필요하면 현재 환경에 맞게 정하며 주요 프로세스 변경은 기록한다.

## 작업 기록과 측정

초기에는 별도 서비스 없이 해당 Issue 또는 관련 요구사항 문서에 아래 기록을 붙인다. Agent가 관찰 가능한 정보를 채우고 Human이 개입 시간과 최종 검수 결과를 보완한다. 외부 Issue 작성은 해당 작업의 권한 범위에서 수행하며, 범위가 제한되면 보고문에 기록 초안을 제공한다.

작업 시작 시 첫 실행 명령으로 시각을 확인한다 (PowerShell 예: `Get-Date -Format o`). 본격적인 분석·구현 전에 시작 시각과 시간대를 작업 기록에 남기고, 검증·자체 리뷰 종료 시에도 시각을 확인한다. 전체 개발 경과 시간은 종료 시각에서 시작 시각을 뺀 값이며 대기를 포함한다. 중단·승인·환경 대기 구간은 별도로 기록한다. 시작 기록을 놓쳤다면 최초 관측 시각과 실제 시작을 구분하고 전체 경과 시간을 추정하여 채우지 않는다. 후속 문서 작업은 원래 구현 시간과 구분하여 측정한다.

| 항목 | 기록 방법 |
| --- | --- |
| 개발 경과 시간 | 시작부터 Agent 검증·리뷰 종료까지의 시각과 경과 시간. 중단·승인·환경 대기를 별도 기록 |
| 최종 수용까지 시간 | 시작부터 Human 최종 수용까지. 아직 수용 전이면 종료값 미기록 |
| 직접 개입 시간 | Human이 요구 정리·질문 응답·결정·검토·직접 수정에 쓴 실제 시간. Agent가 응답 간격으로 추정하지 않음 |
| 요구사항 누락 | 합의된 AC ID와 빠진 동작, 발견 단계. 새 요구 추가는 별도 기록 |
| 결함 | 고유 ID, 증상·영향·발견 단계(검증/자체 리뷰/Human 리뷰/수용 후), 원인·해결 상태. 같은 결함을 중복 집계하지 않음 |
| 수정 횟수 | 최초 구현 후 검증·리뷰 피드백에 따라 수정하고 재검증한 묶음을 1회로 기록. 명령 재실행이나 파일 저장 횟수와 구분 |
| 검증 | 최초 및 최종 결과, 명령·대상·exit code, 미실행/경고, AC와 증거 연결 |
| AI 사용량·비용 | 확인 가능한 도구·모델, 사용량·금액·출처. 구독료 배분 등 추정은 산식 표시. 값이 없으면 미측정 |

경과 시간과 Human 시간을 더해 총 노동 시간으로 해석하지 않는다. 중단 기록 없이 실제 활동 시간을 역산하지 않으며, 미측정과 0을 구분한다. 도구·모델·수용 범위가 달라진 작업은 비교할 때 함께 표시한다.

```text
작업 ID / 요구사항 링크:
기준 commit / 브랜치 / 결과 commit 또는 미커밋 diff:
도구·모델(확인 가능한 범위):
시작 / Agent 검증·리뷰 종료 / Human 수용 시각(시간대 포함):
대기·중단 구간 / 개발 경과 시간:
Human 직접 개입 시간 및 측정·추정 여부:
AC별 결과와 검증 근거:
누락·결함 ID / 발견 단계 / 해결 상태:
수정 회차 및 이유:
AI 사용량·비용 및 출처(없으면 미측정):
미검증·잔여 위험:
Human 검수 결과 / 승인 대상 및 범위:
```

평가 후보는 [ADR 001의 Evaluation](../adr/001-adopt-ai-agent-development.md#evaluation)을 따른다. 초기 기록은 기준선 수집용이며 과거 직접 개발 대비 시간 절감이나 성과를 임의로 산출하지 않는다. 공개할 포트폴리오에는 확인 가능한 결정·변경·검증 근거와 한계를 제시하고 민감한 데이터는 제외한다.

## 향후 확장과 판단 조건

| 순서 | 검토할 변화 | 도입 판단에 필요한 근거 |
| --- | --- | --- |
| 우선 | 자동 테스트·CI 및 실패를 차단하는 품질 관문 | 재현 가능한 테스트와 명령, CI 실패 검출, 적용 브랜치·필수 검사 범위. 도구·권한 설정은 후속 결정 |
| 이후 | 독립 리뷰 | 자체 리뷰에서 놓친 결함의 유형·빈도, Human 검토 부담, 추가 비용 대비 효과 |
| 필요 시 | 멀티 에이전트와 작업 환경 격리 | 독립 작업의 병렬화 이점, 파일 충돌 위험, 통합 책임·검증 방법. Git Worktree 등은 후보 |
| 필요 시 | 오케스트레이션 | 반복적인 작업 배정·상태 추적 비용, 실패 복구·승인 경계 유지 가능성. Herdr 등은 후보일 뿐 선택하지 않음 |

Vitest는 JT-001에서 도입했으며 GitHub Actions는 후속 작업이다. 단일 Agent 기록으로 필요성을 확인한 뒤 확장안과 ADR을 준비한다. 병렬화나 자동화가 Human의 최종 승인 및 운영 변경 승인 경계를 없애지 않는다.

## 운영 개선 이력

### 2026-11-25 — 시작 시각 측정 및 최종 보고 간소화 (Human 승인)

- 근거: JT-001 최종 수용과 함께 Human이 요청한 운영 개선.
- 변경 이유: JT-001은 시작 직후 시각이 없어 전체 개발 경과 시간을 측정하지 못했다. 시작 시각 기록을 첫 실행 단계로 정하여 이후 작업의 측정 누락을 방지한다.
- 보고 개선: 실행 이력과 기술적 근거는 작업 기록·ADR에 보존하고, 최종 보고는 위 다섯 항목과 링크 중심으로 작성한다. 근거의 추적 가능성을 유지하면서 Human이 같은 상세 내용을 반복해서 읽는 부담을 줄이기 위한 변경이다.
- 적용: 향후 작업에 적용하며 이번 승인 반영 문서 작업부터 시작 시각을 기록한다. JT-001의 과거 미측정값은 소급 추정하지 않는다. 지침은 `AGENTS.md`에도 반영했다. 실제 시간 절감·효과는 아직 측정하지 않았다.
